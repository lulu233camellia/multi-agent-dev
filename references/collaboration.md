# 协作与交接

仅在真正需要多个执行者、独立验收或长期团队时读取。

## 选择执行载体

| 已有条件 | 操作 |
| --- | --- |
| 用户已有长期规划 / 开发 / 验收聊天 | 读取登记，核实目标仍有效，沿用当前路由 |
| 用户明确要求创建长期团队 | 使用当前环境提供的聊天管理工具建立所需角色，登记真实 ID 与职责；无工具则交付初始化文本，不能声称已经创建 |
| 当前任务获准使用子代理 | 为独立写入面分配开发者，需要独立验收时使用不同执行上下文的只读审核者 |
| 未授权或没有代理能力 | 主 Agent 完成可独立推进的工作，说明独立验收缺口；不得编造其他角色已完成工作 |

发现和使用当前环境真实提供的工具，不照抄其他客户端的命令。对子代理使用原生消息和等待工具；已有长期聊天使用聊天工具。长时间等待使用有界等待，遵循宿主的进度沟通要求，不进行高频轮询。工具返回的完成状态只代表调用结束，必须读取产物和结论。

## 最小任务包

先形成一个简短、所有角色共享的约定；可以放在已有任务卡里：

```text
工作项：项目内唯一 ID
当前阶段 / 本轮里程碑：
目标及首要可用结果：
本次范围 / 不做事项：
验收条件：可观察的输入、行为与结果
当前基线：分支 / base commit / 当前候选内容标识
权威文件：当前任务书、相关项目规则
写入所有权：执行者 → 允许写入的路径；共享文件 Owner
检查：必要专项、必需 CI、真实环境或人工验证
当前授权：允许实施 / 已授权外部动作与限额 / 仍缺的决定
审核预算：按 SKILL.md；已有项目要求或用户约定优先
交付位置与下一接收方：
```

需求已足够明确时，协调者直接整理，不先制造一轮需求审批。关键行为有歧义才请求决策，同时推进不依赖答案的工作。

开发者只收到执行所需的当前事实、范围和接口；不要转发完整历史对话或已经否决的方案。审核者收到独立判断所需的需求、完整首轮 diff、证据、已知问题状态和相关项目规则，不收到“必须通过”或预设答案。

## 文件组织

已有项目使用 `00-产品交接单`、`01-开发交付单`、`02-验收报告`、`03-消息记录` 时复用它们，把审核状态放入 `02`，不再创建第二套事实源。

新项目只建立实际需要的记录：一个任务文件可以容纳范围、实现和审核状态。长期团队才需要登记表；登记字段为角色、当前真实 ID、职责、写入范围、状态。任务迁移更新登记，旧 ID 仅留作历史，不继续派发。

记录中的当前要求与历史分开；变更原因和旧结论放历史区，不混入供执行者读取的当前约定。

## 交接闭环

每次只发送短通知，内容指向已经写好的权威产物：

```text
消息 ID：工作项 + 阶段 + 序号
类型：PLAN_TO_DEV / DEV_TO_QA / QA_TO_DEV / QA_PASS / BLOCKED
from / to：真实角色及已核实 ID
工作项 / 当前候选 / 当前审核轮：
产物位置：
本次完成或发现：
要求下一方做什么：
```

- 开发完成：交付实现与检查证据，通知验收者。
- 验收完成：报告结论及稳定问题 ID；需修复则返回开发者，通过或受阻则通知协调者。
- 协调者：读取实际报告并向用户交付结果，不能只转述其他 Agent 的“完成”。
- 同一个问题或同一候选的重复消息按消息 ID 去重；不能触发重复实现或新一轮审核。
- 投递失败先确认目标状态；确需重发时最多一次。仍失败则记录 `delivery_degraded`，说明文件已到哪一步，不能假定收件人已处理。

本工作流只使用获准的项目代理协作通道。它不授予向同事发送邮件、钉钉、飞书或 Slack 消息的权限。

## 并行的边界

并行收益来自独立工作面，不来自同一件事重复执行。多个开发者互不覆盖文件；集成由指定 Owner 完成。不要为普通任务默认启动竞赛、多个相同审核者或“审核者的审核者”。高风险专项可分开覆盖不同问题，并在同一轮统一合并发现。

复审可使用之前的验收者，也可迁移到新上下文；两者都必须读取同一份问题状态和有效证据。上下文切换不影响工作项的审核计数。
