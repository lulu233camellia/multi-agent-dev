# 技术方案：固定影响协作的关键决定

仅在产品行为已足够明确、但现有技术约定不足以支持实现时读取。小改动沿用当前架构；已有项目只设计受影响部分。

## 先调查现状与约束

读取相关代码、依赖和锁文件、接口、数据结构、运行配置及已有决策。区分已经运行的事实、文档中的意图和本次提案；发生冲突时追到实际拥有该行为的代码或配置。

确认本轮需要的约束：运行平台、数据敏感程度、已有服务、可接受成本、工作负载和失败后果。缺少可靠容量数据时明确假设，避免用虚构流量支持选型。需要确定外部技术当前能力或版本时查其官方资料；不为写方案而更新项目依赖。

## 只决定会造成不兼容或实质返工的事项

判断一个决定是否需要提前固定：不同开发者独立实现时，是否可能选择互不兼容的行为？若会，且现有代码没有明确约定，就在共同方案中作出决定。

| 需要协调的方面 | 最小约定 |
| --- | --- |
| 模块与写入所有权 | 每个模块负责什么、依赖方向、共享文件或数据由谁维护 |
| 数据与状态 | 实体关系、状态变化及由谁修改；哪些操作需要一致性或去重 |
| 接口 | 调用方与提供方、输入输出、错误含义；并行开发前对齐实际需要的字段与名称 |
| 外部服务 | 依赖能力、失败时的产品行为、哪些部分尚未在真实环境验证 |
| 运行与交付 | 本轮运行环境、必要配置、启动与验证方法；涉及发布或数据变更时补相应恢复办法 |

不要对每个项目强制引入队列、缓存、微服务或复杂状态机。团队人数、记录条数等经验值只能帮助提出问题，不能单独决定技术方案。

## 比较真实可选方案

有重大取舍时，记录当前约束、可行选项、推荐、理由和接受的代价；短决定可以几句话，长期共享决定再用项目已有 ADR 格式。

优先考察是否能复用现有能力。只有存在实质差异才比较多个方案；不因模板要求额外设计一套“理想架构”。让用户决定产品范围、费用承诺或难以逆转的取舍，执行者负责授权范围内的普通工程选择。

不把未获用户确认的偏好写成已批准决定。已有项目约定直接继承；需要变更时说明具体冲突及影响。

## 用小实验消除关键未知

第三方接口能力、模型输出、关键性能或迁移行为若决定方案成败，先设计最小实验：

- 实验回答哪个具体问题；输入、环境和成功 / 失败判据是什么。
- 允许使用哪些资源；是否已有相应外部调用、费用或数据操作授权。
- 结果支持哪些结论，不能证明什么；失败后采用什么替代方案。

已有仍有效的实验结果直接复用。没有真实环境时可以做局部或模拟验证，但明确剩余证据缺口；不把所有开发停在与其无关的等待上。

## 交给开发的最小信息

把本轮产品行为对应到可运行的实现增量，每个任务说明：目标行为、负责模块或文件、依赖、接口、相关检查和交付顺序。独立任务可以并行，共享文件由一个负责人集成。

对照产品验收条件检查一次：核心行为是否有对应实现任务，模块间约定是否一致，是否遗漏影响交付的关键未知。满足后继续已授权实现；不另起固定的“架构审核—PRD 审核—计划审核”流水线。

若实现中出现新事实，只调整受影响的决定、接口与任务，沿用未受影响的方案和有效证据。确需独立方案审核时，复用主 Skill 的问题记录与审核预算，不另建重复循环。
